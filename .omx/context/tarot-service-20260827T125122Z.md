# Autopilot Context: Korean Three-Card Tarot Service

## Task statement

Build and verify a production-ready, Korean, mobile-first three-card tarot web service from an empty repository. The complete product contract is in the attached mission document at `/Users/joelonsw/.codex/attachments/243d09c6-7b83-4a13-9891-072ff53360ae/pasted-text.txt`.

## Desired outcome

A deployable web experience in which a reader welcomes the visitor, the visitor may enter a question, a real 78-card deck is shuffled and spread, three cards are selected and revealed, a skippable affiliate interstitial appears, one connected Korean reading is shown, and the result can be shared or restarted without a reload.

## Known facts and evidence

- Repository contains only a placeholder README and the initial Git commit.
- Node.js 20.15.1, npm 10.7.0, and pnpm 11.19.0 are available.
- The user explicitly requires repository-backed project memory, resumable 76,076-combination generation, mobile visual QA, and multi-agent/model routing when supported.
- Runtime supports delegated agents and explicit Sol/Terra/Luna model selection.
- The service must not depend on runtime LLM calls for normal reading lookup.

## Constraints

- Korean copy must be restrained and human, with no AI-service language.
- Full 78-card Fisher-Yates shuffle, no reversals, no duplicate selection.
- Affiliate click cannot gate results; URL absence and feature disablement must be safe.
- User questions must not be exposed in share URLs.
- Artwork licensing must be explicit; placeholder or original assets are preferred when provenance is uncertain.
- 76,076 readings must not block a complete product flow using sample/fallback readings.
- Mobile-first, accessible, reduced-motion aware, and performant with 78 card backs.
- No unnecessary dependencies.

## Unknowns / open questions resolved by reversible defaults

- Brand: use the mission's working title `오늘의 타로` until a better validated name emerges.
- Hosting: target Vercel-compatible Next.js output while retaining portable domain/data modules.
- Persistence: encode share state in a compact opaque payload that excludes the question unless a server-backed share store is demonstrably needed.
- Artwork: create original, stylized symbolic artwork and card backs for V1; do not ship unverified RWS scans.
- Reading coverage: ship curated samples plus a deterministic card-aware fallback, while the generation CLI supports gradual replacement with all pre-generated combinations.
